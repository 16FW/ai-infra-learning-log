# Lesson 05. LLM Basics: 언어 모델 직접 돌려 보기

## 핵심 개념
- LLM은 지금까지의 토큰을 보고 다음 토큰의 확률분포를 내는 모델이고, 토큰을 하나씩 붙여 가며 생성한다(자기회귀). 토큰 수가 지연·메모리·비용의 단위가 된다.
- 한 요청은 두 단계다. prefill은 프롬프트 전체를 병렬로 처리하고, decode는 토큰을 하나씩 만든다. decode는 매 토큰마다 가중치를 읽어야 해서 메모리 읽기 속도에 묶인다.
- KV cache는 앞 토큰들의 key/value를 저장해 재계산을 없앤다. 대신 메모리를 쓰고, 크기는 토큰 수와 배치에 비례한다.
  - 토큰당 KV cache ≈ 2 × 레이어 수 × (KV 헤드 수 × 헤드 크기) × 바이트
- 샘플링: greedy는 재현 가능하지만 반복 루프에 빠질 수 있고, temperature/top-k/top-p는 다양성을 높이는 대신 재현성이 낮아진다(시드 고정 시 같은 환경에서 재현).
- 컨텍스트 길이(gpt2는 1024)와 max_new_tokens는 요청 하나가 쓸 수 있는 자원의 상한이다.

## 동작 원리
- gpt2의 토크나이저는 byte-level BPE다. 한글 "나"는 UTF-8 3바이트라 3토큰으로 나뉘었다.
- `generate`의 `max_new_tokens`는 새로 만들 토큰 수이고, `max_length`는 프롬프트까지 포함한 길이다. 토크나이저 결과에는 `input_ids`와 `attention_mask`가 있고, gpt2는 pad 토큰이 없어 `pad_token_id=eos_token_id`를 넘겼다.
- 가중치는 지연 로딩(mmap)되는 것으로 보인다. fp32 로드 직후 RssFile이 94.6MiB였다가 첫 생성 후 573.1MiB(+478.5MiB ≈ 가중치 474.7MiB)로 늘었고, RssAnon은 거의 그대로(277.9 → 282.7MiB)였다.
- 캐시를 끄면 매 스텝이 앞 토큰 전체를 다시 계산해서, 생성 길이가 늘수록 시간이 선형보다 빠르게 늘어난다(80/20 시간 비율 7.11).

## 실습에서 한 것
- 토크나이저: 영어 37글자 → 9토큰, 한국어 24글자 → 49토큰(이 문장 쌍, gpt2 토크나이저 기준 약 5.4배), 코드 28글자 → 11토큰.
- gpt2 생성: greedy는 반복 실행해도 같았고, "open-source"가 반복되는 루프에 빠졌다. 샘플링은 매번 달랐고 시드 고정 시 같았다.
- 메모리: 파라미터 124,439,808개(fp32 474.7MiB, bf16 237.4MiB, 계산값), KV cache(gpt2, 1024토큰, fp32, 계산값) 배치 1 = 72MiB, 배치 8 = 576MiB. 실측 RSS는 로드 직후 372.6MiB, 첫 생성 후 855.8MiB.
- 속도(CPU, torch 스레드 2 / nproc 4): 프롬프트 10토큰은 첫 토큰 39.3ms, 토큰당 28.1ms(35.6 tokens/s), 400토큰은 첫 토큰 673.8ms, 토큰당 31.5ms.
- use_cache 비교(ms): True 500/1096/2005, False 1113/2714/7915 (n=20/40/80), 80/20 비율 True 4.01, False 7.11, 출력은 동일.
- FastAPI 서버(`llm_api.py`): 시작 시 로드와 워밍업 후 `/ready` 200(준비 전 503, 약 9.5초). 입력 검증은 빈 prompt와 max_new_tokens 초과가 422, 컨텍스트 초과가 400이다. 동시 요청 4건은 락에 의해 직렬 처리되어 2013/3990/6211/8523ms로 끝났고(1건은 1907ms), 처리량은 0.52 → 0.47건/s로 늘지 않았다. 절대 시간은 백그라운드 부하로 평소보다 느렸고, 비율 기준으로 해석했다.

## Infrastructure 연결
- 입력 검증(컨텍스트, max_new_tokens)은 요청 하나가 서버 자원을 독점하지 못하게 하는 자원 보호다.
- 메모리 request는 로드 직후(372.6MiB)가 아니라 워밍업 후(855.8MiB) RSS와 KV cache 예산으로 잡는다. 7B급은 가중치(약 13GiB)에 더해 KV cache(32층·hidden 4096, fp16, 4096토큰 기준 계산: 배치 1에서 2GiB, 배치 16에서 32GiB)를 계산한다.
- `/health`(프로세스 생존)와 `/ready`(로드와 워밍업 완료)를 분리하고, 로드가 길면 startupProbe로 시간을 번다.
- CPU 한 대에서는 동시 요청이 직렬화되어 처리량이 늘지 않으므로 배칭(continuous batching), replica, GPU가 필요하다.
- 향후 개선: 대기열이 길면 429/503으로 빨리 거절(admission control).

## 면접 포인트
- prefill vs decode, KV cache의 이득과 비용(토큰·배치에 비례), 토큰 수가 비용이 되는 이유.
- OOMKilled는 anon 메모리(RssAnon) 증가인지 부하 피크인지 구분하고, 부하 테스트로 피크 working set을 측정해 limit을 정한다.

## 내 말로 3줄 요약
1. LLM 서빙은 토큰 단위로 생각해야 한다. 토큰 수가 지연(decode는 토큰당 약 30ms로 선형)과 메모리(KV cache)와 비용을 정하고, 같은 내용도 토크나이저에 따라 토큰 수가 크게 달라진다(이번 문장 쌍은 영어 9 vs 한국어 49).
2. prefill은 병렬이라 토큰당 약 1.6ms, decode는 한 토큰씩 가중치를 읽어 토큰당 약 30ms다. KV cache는 재계산을 없애 80토큰에서 약 3.9배 빠르게 하지만 토큰 수와 배치에 비례해 메모리를 쓴다.
3. 서버는 시작 때 로드와 워밍업을 끝내고 `/ready`로 알리며, 컨텍스트와 max_new_tokens를 검증하고, 메모리는 첫 생성 후 RSS와 KV cache 예산으로 잡아야 한다. CPU에서는 동시 요청이 직렬화되어 처리량이 늘지 않으므로 배칭이나 replica가 필요하다.
