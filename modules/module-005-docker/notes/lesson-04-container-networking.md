# Lesson 4. 컨테이너 네트워킹

## 핵심 개념
- 컨테이너는 자기만의 네트워크 공간(namespace)을 가져서, 컨테이너 안의 `localhost`(127.0.0.1)는 자기 자신이다.
- 밖에서 접속하려면 `-p 호스트포트:컨테이너포트`가 필요하고, 앱은 `0.0.0.0`에서 요청을 받아야 한다.
- 기본 `bridge`는 이름 DNS가 없어 IP로만 통신하고, 사용자 정의 `bridge`는 내장 DNS(127.0.0.11)로 컨테이너 이름을 풀어 준다.
- 네트워크는 격리 단위다. 서로 다른 네트워크의 컨테이너는 이름을 모르고, 한 컨테이너를 두 네트워크에 연결하면 양쪽에서 부를 수 있다.

## 동작 원리
- `-p`는 호스트 포트로 들어온 요청을 컨테이너의 외부 주소(eth0)로 전달한다. 앱이 127.0.0.1에서만 들으면 그 주소에는 받는 프로그램이 없어 연결이 끊긴다(exit 56).
- `-p`가 아예 없으면 호스트 쪽 창구가 없어 연결 자체가 안 된다(exit 7).
- 기본 `bridge`의 `resolv.conf`는 호스트 쪽 DNS(192.168.65.7)를 가리켜 컨테이너 이름을 모르고, 사용자 정의 `bridge`는 127.0.0.11이 컨테이너 이름을 풀고 모르는 이름만 바깥 DNS로 넘긴다.
- 컨테이너 IP는 재생성 때 바뀔 수 있어서(172.20.0.2 → 172.20.0.3) 이름으로 부르는 구조가 필요하다.
- 컨테이너에서 외부로 나가는 트래픽은 호스트를 통해 NAT되어 나간다(`example.com` HTTP 200).

## 실습에서 한 것
- 바인딩: `--host 127.0.0.1`은 호스트 curl이 exit 56, 컨테이너 안에서는 성공했고, `0.0.0.0`은 호스트 curl이 성공했다. `docker port`는 둘 다 0.0.0.0:8000이었고 `docker logs`의 바인딩 주소만 달랐다.
- 이름 통신: 기본 `bridge`에서 이름은 exit 28(시간 초과), IP(172.17.0.2)는 성공했고, 사용자 정의 `bridge`에서는 이름이 성공했다. 28이 나온 이유는 `curl -m 3` 안에 DNS 조회가 끝나지 않았기 때문이다.
- 격리: netA에서 netB의 `b1`은 `Could not resolve host`(exit 6), `docker network connect netA b1` 후에는 성공했다.
- 서비스 간 통신: `-p` 없이 appnet 안에서 client → api(`/predict?x=3`)가 `{"y":6.0}`로 성공했고, 호스트 curl은 exit 7이었다. api를 재생성하자 IP가 .2에서 .3으로 바뀌었지만 이름 호출은 계속 성공했다.

## Infrastructure 연결
- 사용자 정의 네트워크 DNS는 Kubernetes Service DNS와 같은 발상이고, `-p`는 Ingress/LoadBalancer, 내부 통신은 ClusterIP에 해당한다.
- 한 컨테이너를 두 네트워크에 걸치는 구조는 입구(게이트웨이) 패턴의 기초이고, Compose의 frontend/backend 네트워크, Kubernetes의 NetworkPolicy로 이어진다.
- 모델 서버와 DB는 외부에 노출하지 않고 API 하나만 입구로 둔다.

## 면접 포인트
- "앱은 떠 있는데 포트 매핑해도 접속이 안 된다"면 바인딩 주소(127.0.0.1 vs 0.0.0.0)부터 확인한다.

## 내 말로 3줄 요약
1. 컨테이너의 `localhost`는 자기 자신이라, 밖에서 접속하려면 `-p`로 포트를 열고 앱은 `0.0.0.0`에서 들어야 한다.
2. 컨테이너끼리 이름으로 통신하려면 사용자 정의 bridge를 써야 하고(내장 DNS), 컨테이너 IP는 재생성 때 바뀌므로 이름으로 부른다.
3. 네트워크를 나누면 격리가 되므로 입구 API 하나만 `-p`로 열고 모델 서버와 DB는 안쪽 네트워크에 숨겨서 공격 표면을 줄인다.
