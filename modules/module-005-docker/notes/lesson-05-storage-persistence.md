# Lesson 5. 저장 및 데이터 영구 보존

## 핵심 개념
- 이미지는 읽기 전용이고 컨테이너에는 쓰기 가능한 레이어가 얹힌다. 이 레이어의 수명은 컨테이너와 같아서 `stop/start`는 유지되고 `rm`하면 사라진다.
- 볼륨(volume)은 Docker가 관리하는 이름 기반 저장소로, 컨테이너가 사라져도 남는다(DB, 체크포인트).
- 바인드 마운트(bind mount)는 호스트의 지정 경로를 그대로 연결한다(개발 중 코드, 설정). 호스트 경로와 UID에 의존한다.
- `:ro`로 마운트하면 컨테이너가 그 경로에 쓰지 못한다. `tmpfs`는 메모리에만 두어 종료되면 사라진다.

## 동작 원리
- `docker diff`로 쓰기 레이어에 쌓인 변경(A 추가, C 변경)을 볼 수 있다. Python은 `__pycache__`도 남긴다.
- 파일 소유자는 이름이 아니라 숫자 UID로 기록된다. 컨테이너가 root(UID 0)로 실행되면 호스트에서도 root 소유로 보인다.
- 볼륨의 `Mountpoint`(`/var/lib/docker/volumes/...`)는 Docker Desktop에서는 Docker 쪽 VM 안의 경로라 내 Ubuntu에서 직접 보이지 않는다.
- 읽기 전용 마운트에 쓰면 `OSError: [Errno 30] Read-only file system`이 난다.

## 실습에서 한 것
- 쓰기 레이어: 볼륨 없이 같은 컨테이너를 재시작하면 횟수가 1에서 2로 유지됐고, 새 컨테이너는 1부터 시작했다.
- 볼륨: `-v cnt:/data` + `--rm`으로 3번 실행하면 1, 2, 3으로 남았고, 볼륨 없이는 1, 1, 1이었다.
- 바인드 마운트: 컨테이너가 만든 파일이 호스트에서 `root:root`(644)라서 내 계정으로 수정이 Permission denied였다. `--user "$(id -u):$(id -g)"`로 실행하면 소유자가 내 계정이 되어 수정됐다. `:ro`에서는 쓰기가 Errno 30으로 막혔다.
- 모델 모사: `models/`의 모델 파일(10MB)을 `:ro`로 마운트해 읽고, 이미지를 다시 빌드하지 않고 새 파일(15MB)로 교체해 읽었다.

## Infrastructure 연결
- 볼륨은 Kubernetes의 PV/PVC와 같은 발상이다. 컨테이너(Pod)는 언제든 교체되므로 지속돼야 하는 데이터는 밖에 둔다.
- 모델 파일은 이미지에 `COPY`(태그 하나로 코드와 모델 고정, 롤백 쉬움, 이미지가 커짐)하거나 읽기 전용 볼륨(이미지가 작고 재빌드 없이 교체, 버전과 공유 저장소를 따로 관리)으로 둔다.
- 노드 여러 대가 동시에 큰 이미지를 받으면 레지스트리가 병목이 되므로 롤링 배포로 분산한다.
- 비 root 실행(`--user`)과 `:ro` 마운트는 컨테이너가 호스트 파일을 바꿀 수 있는 범위를 줄인다.

## 면접 포인트
- 컨테이너를 재배포했더니 데이터가 사라졌다면, 그 데이터가 쓰기 레이어에만 있었는지(볼륨 없음)를 먼저 확인한다.

## 내 말로 3줄 요약
1. 컨테이너 안에 쓴 데이터는 컨테이너 수명과 같아서 `rm`하면 사라지므로, 남겨야 할 데이터는 볼륨이나 바인드 마운트로 밖에 둔다.
2. 바인드 마운트의 파일 소유자는 숫자 UID라서 컨테이너가 root면 호스트에서 수정이 안 되고, `--user`로 내 UID로 실행하면 해결된다.
3. 모델 파일은 이미지에 넣으면 재현과 롤백이 쉽고, 볼륨(`:ro`)에 두면 이미지가 가볍고 재빌드 없이 교체할 수 있어서, 규모와 공유 저장소 유무로 고른다.
