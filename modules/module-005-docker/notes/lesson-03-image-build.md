# Lesson 3. 도커 이미지 빌드

## 핵심 개념
- `FROM`, `COPY`, `RUN`은 레이어를 만들고, `CMD`, `ENV`, `ARG`는 설정 정보만 남긴다.
- 빌드 캐시는 위에서부터 입력이 같으면 재사용하고, 처음 바뀐 단계부터 아래가 모두 무효가 된다. 그래서 잘 안 바뀌는 `requirements.txt`를 먼저 설치하고 코드를 나중에 복사한다.
- `.dockerignore`는 빌드 컨텍스트에서 파일을 제외한다(전송 크기, 속도, 비밀 유출 방지).
- multi-stage build는 빌드 단계의 결과물만 `COPY --from=builder`로 최종 이미지에 가져와서, 빌드 도구와 캐시를 최종 이미지에서 뺀다.

## 동작 원리
- `main.py`만 고쳐도 `COPY . ` 단계 캐시가 깨지므로, 그 아래의 `pip install`까지 다시 실행된다(v1 구조).
- `pip install`에 `--no-cache-dir`가 없으면 pip 캐시(`/root/.cache/pip`, 약 15MB)가 레이어에 남는다.
- BuildKit은 `COPY`가 쓰는 파일만 빌드 컨텍스트로 전송한다. `COPY app`만 쓰면 큰 파일이 있어도 전송량이 거의 같고, `COPY . /ctx`면 전체가 전송된다.
- `docker images`의 SIZE는 이 환경에서 `docker history` 레이어 합과 맞지 않아, 레이어별 크기는 `docker history`로 비교했다.

## 실습에서 한 것
- 측정 조건: nproc=4, load average 약 3, 캐시 있는 재빌드 기준.
- 캐시 순서: 코드만 바꿨을 때 v1은 pip 단계가 26~32초로 다시 실행되어 전체 43~48초, v2는 pip 단계가 CACHED라 전체 6.5초(약 7배).
- multi-stage: 의존성 레이어가 v2 69.2MB에서 44.8MB로, 전체는 약 203MB에서 179MB로 줄었다. 차이 24.4MB 중 15MB는 pip 캐시, 나머지 약 9MB는 확인하지 못했다.
- `.dockerignore`: `COPY . /ctx` 보강 실험에서 컨텍스트가 104.89MB(5.4초)에서 320B(0.1초)로 줄었다.
- 두 이미지 모두 `/health`가 정상 응답했다.

## Infrastructure 연결
- 이미지가 작을수록 스케일아웃 때 노드가 이미지를 받는 시간이 줄고, 새 Pod가 뜨는 시간이 짧아진다.
- ML 이미지는 `의존성 → 모델 가중치 → 코드` 순서로 쌓고, CUDA 포함 torch는 CPU 서빙이라면 CPU 빌드로 교체한다.
- 컴파일러가 필요한 패키지를 빌드할 때 multi-stage의 효과가 커진다.

## 면접 포인트
- 이미지가 크거나 빌드가 느리면 `docker history`로 큰 레이어와 캐시가 깨지는 지점부터 본다.

## 내 말로 3줄 요약
1. Dockerfile은 위에서부터 캐시가 이어지므로 자주 바뀌는 코드는 아래에, 의존성은 위에 두면 재빌드가 7배 빨라진다.
2. `.dockerignore`는 크기와 속도뿐 아니라 `.env`, `.git` 같은 비밀이 이미지 레이어에 남는 걸 막아 준다.
3. multi-stage는 빌드 도구와 캐시를 최종 이미지에서 빼서 크기와 공격 표면을 줄이고, 이득은 컴파일이 필요한 패키지일수록 커진다.
