# Lesson 01 — 파일시스템 계층과 링크

## 핵심 개념

### 모든 것은 파일이다

리눅스는 커널 내부 상태까지 파일처럼 노출한다. `/proc`은 디스크에 실재하지 않는
가상 파일시스템이고, 커널이 자기 상태를 파일 인터페이스로 보여주는 창구다.

```
/proc/cpuinfo      CPU 정보
/proc/meminfo      메모리 정보
/proc/<PID>/       프로세스별 디렉토리
```

Python의 `os.cpu_count()`나 `shutil.disk_usage()`도 결국 이 경로를 통해 커널에게
물어본 결과다.

### FHS — 어느 동네에 무엇이 있는가

정적/동적, 시스템/사용자 두 축으로 나뉜다.

| 경로 | 담는 것 |
|---|---|
| `/etc` | 시스템 전역 **설정** (정적) |
| `/var` | 운영 중 변하는 데이터 (로그, DB, 캐시) |
| `/usr` | 설치된 프로그램·라이브러리 (Unix System Resources, 사용자 파일 아님) |
| `/tmp` | 임시 파일, 재부팅 시 소멸 |
| `/opt` | 패키지 매니저 밖에서 설치한 서드파티 |
| `/proc` | 커널 상태 (가상 FS) |
| `/run` | 런타임 상태, tmpfs(메모리) |

`which python3` → `/usr/bin/python3`. `/usr`의 정체가 여기서 확인된다.

### inode와 링크

파일의 실체는 inode이고, 파일 이름은 inode를 가리키는 라벨이다.

| | 하드 링크 | 심볼릭 링크 |
|---|---|---|
| inode | 원본과 동일 | 별도 할당 |
| 저장 내용 | (같은 데이터 참조) | **원본 경로 문자열** |
| 원본 삭제 시 | 멀쩡히 읽힘 | 깨짐 |
| 크기 | 원본과 동일 | 경로 문자열 길이 |
| `ls -l` 표시 | `-rw-r--r--` | `lrwxrwxrwx` |

심볼릭 링크의 `lrwxrwxrwx`(777)는 표시일 뿐 의미가 없다. 실제 접근 제어는
가리키는 **원본 파일의 권한**으로 결정된다.

## 동작 원리

### `rm`이 실제로 하는 일

`rm`은 데이터를 지우는 명령이 아니다. 디렉토리에서 이름 하나를 떼어내고
**link count를 1 줄이는 것**뿐이다. count가 0이 되어야 커널이 데이터 블록을
회수한다.

```
101394 -rw-r--r-- 2  hard.txt        ← link count 2
101394 -rw-r--r-- 2  original.txt       (같은 inode를 두 이름이 공유)
        ↓ rm original.txt
101394 -rw-r--r-- 1  hard.txt        ← 1로 감소, 데이터는 그대로
```

### 삭제했는데 디스크가 안 비는 이유

프로세스가 파일을 열고 있으면 **열린 파일 디스크립터(fd)도 참조로 잡힌다.**
이름이 0개여도 fd가 남아 있으면 블록이 회수되지 않는다.

```
200MB 파일 생성 → df: 5.6G
tail -f 로 열어둔 채 rm → df: 5.6G   (변화 없음)
tail 종료 → df: 5.4G                 (그제야 반환)
```

`ls`에는 안 보이는데 디스크는 차 있는 상태 = deleted-but-open file.

**대응 순서**
1. `df -h` — 어느 파일시스템이 찼는지
2. `du -sh /var/log/* | sort -h` — 범인 디렉토리
3. 지웠는데 안 줄면 `lsof | grep deleted`
4. 프로세스를 못 내리면 `truncate -s 0 <파일>` (fd 유지, 내용만 비움)

### find의 조건은 위험도 추가한다

`-type f`는 일반 파일만 고른다. 그래서 `/etc/resolv.conf`(심볼릭 링크)가
검색 결과에서 빠졌다. 결과가 예상보다 적으면 **먼저 의심할 것은 내가 건 조건**이다.

```bash
find /etc -name "*resolv*" 2>/dev/null     # -type f 빼야 링크도 나옴
```

`2>/dev/null` — 리눅스에는 stdout과 stderr 두 개의 출구가 있고, `2>`는
stderr만 버린다.

## 실습에서 한 것

- `/proc/cpuinfo`에서 `grep -c "^processor"`로 논리 프로세서 수 확인 → 8
  (물리 코어 4 + 하이퍼스레딩. 성능 향상은 2배가 아니라 20~30%)
- `free -h`로 메모리 확인. **실사용 가능량은 `free`가 아니라 `available`**
  (리눅스는 남는 메모리를 디스크 캐시로 쓰고, 필요하면 즉시 회수한다)
- 하드/심볼릭 링크를 만들고 원본 삭제 전후의 inode와 link count를 비교
- 터미널 두 개로 deleted-but-open 파일을 재현하고 `df` 수치 변화를 3시점 관찰

## Infrastructure 연결

### 심볼릭 링크 기반 모델 배포

```
/models/
├── model-09-01.pkl
├── model-09-07.pkl
└── current -> model-09-01.pkl   ← 서빙 코드는 이것만 읽음
```

파일 복사 없이 링크만 교체하면 수 GB 모델도 즉시 배포·롤백된다.

단, `ln -sf`는 "기존 링크 삭제 → 새 링크 생성" 2단계라 그 찰나에 `current`가
존재하지 않는다. 원자적 교체가 필요하면:

```bash
ln -sfn model-09-07.pkl current.tmp && mv -T current.tmp current
```

> 배포에서 "잠깐 없는 상태"가 생기면 그건 다운타임이다.

**한계**: 링크를 바꿔도 이미 메모리에 올라간 모델은 그대로다. 프로세스를
재시작해야 적용되고, 그래서 다운타임이 생긴다. 이걸 푸는 게 K8s Rolling Update.

### systemd와 심볼릭 링크

`systemctl enable`이 하는 일 = `*.wants/` 디렉토리에 심볼릭 링크 생성.
부팅 시 systemd가 그 디렉토리를 읽어 시작 대상을 결정한다.

### 그 외

- `/etc/resolv.conf`는 Pod 안에도 있고 CoreDNS 주소가 들어간다.
  "Pod에서 서비스 이름으로 접속이 안 된다"의 1순위 확인 지점.
- 하이퍼스레딩: K8s `resources.limits.cpu`는 논리 프로세서 기준이다.
  물리 코어와 혼동하면 리소스 산정이 틀어진다.
- `/tmp`에 모델을 받아두면 Pod 재시작 때 날아간다.

## 면접 포인트

- 하드 링크와 심볼릭 링크를 inode 관점에서 설명할 수 있어야 한다.
- "로그를 지웠는데 `df`가 그대로다" → 열린 fd 때문. `lsof | grep deleted`로 확인.
- 무중단 배포를 심볼릭 링크로 설계하고, **그 방식의 한계(메모리 반영 안 됨)**까지
  말하는 것이 핵심.

## 내 말로 3줄 요약

1. 리눅스의 모든 것은 파일이다: 커널 내부 정보도 가상 파일시스템(`/proc`) 경로를 통해
   파일처럼 읽고 확인한다.
2. 파일의 실체는 inode다: 파일명은 그저 라벨일 뿐이며, 원본을 지워도 데이터가 남는
   하드 링크와 단순 경로 참조인 심볼릭 링크로 나뉜다.
3. 용량 미반환은 열린 프로세스(fd) 때문이다: 파일(이름)을 지워도 프로세스가 잡고 있으면
   용량이 안 비워지므로, `lsof`로 확인한 뒤 해당 프로세스를 재시작하거나 `truncate`로
   내용을 비워야 한다.
