# Lesson 02 — 권한과 소유권

## 핵심 개념

### 3×3 격자

```
-rw-r--r--
│ │  │  └── 기타(other)   r--
│ │  └───── 그룹(group)   r--
│ └──────── 소유자(user)  rw-
└────────── 파일 종류 (- 일반, d 디렉토리, l 심볼릭 링크)
```

비트 값: `r=4`, `w=2`, `x=1`

| 숫자 | 문자 | 숫자 | 문자 |
|---|---|---|---|
| 600 | `rw-------` | 755 | `rwxr-xr-x` |
| 640 | `rw-r-----` | 775 | `rwxrwxr-x` |
| 700 | `rwx------` | 444 | `r--r--r--` |

**`0`은 `x`가 아니라 무권한(`---`)이다.**

### 커널은 첫 매칭에서 멈춘다

소유자라면 소유자 비트만 적용된다. 그룹/기타 권한이 아무리 널널해도
소유자 권한이 막으면 막힌다. (Python `except` 절이 위에서 아래로 첫 매칭에서
멈추는 것과 같은 구조)

그래서 권한을 볼 때 질문은 "이 파일의 권한이 뭔가"가 아니라
**"지금 접근하는 주체가 소유자인가, 그룹인가, 기타인가"**다.

### 디렉토리의 r과 x는 파일과 의미가 다르다

디렉토리는 **"이름 → inode" 대응표를 담은 특수한 파일**이다.

- `r` = 대응표에서 **이름 목록을 조회**할 권한
- `x` = 그 이름을 따라 **실제 inode에 도달**할 권한 (통과, traverse)

| 디렉토리 권한 | `ls dir` | `cat dir/file` |
|---|---|---|
| `r`만 (`644`) | 이름은 나오나 상세 정보 실패 | ✗ |
| `x`만 (`711`) | ✗ | ✓ |
| `r+x` (`755`) | ✓ | ✓ |

`711`은 "이름을 정확히 아는 사람만 접근 가능, 둘러보기는 불가"라서 웹 서버
디렉토리 목록 노출을 막을 때 쓴다. 디렉토리는 통과(`x`)가 없으면 쓸모가 없어서
`755`가 표준이다.

### 파일 읽기 조건

```
파일 내용 읽기 = (경로상 모든 디렉토리의 x) AND (파일 자신의 r)
```

디렉토리의 `x`는 **문을 통과할 권한**이지 방 안의 물건을 볼 권한이 아니다.
`chmod 755 dir` + `chmod 000 file` → `cat`은 여전히 실패한다.

## 동작 원리

### 실행 시 검사 순서

```
./script.sh
   ↓
① 커널: x 비트 검사 → 없으면 Permission denied (내용은 보지도 않음)
   ↓ 통과
② 커널: 첫 바이트 확인 → #! 있으면 그 인터프리터, 없으면 호출 셸이 처리
   ↓
③ 실행
```

권한 검사가 내용 해석보다 먼저다. `Permission denied`면 shebang을 아무리
들여다봐도 소용없다.

### 경로 전체 확인

```bash
namei -l /data/models/data.txt
```

`/`부터 최종 파일까지 각 단계의 권한을 나열해준다. 파일 권한은 정상인데
`Permission denied`가 날 때 쓴다.

### 777이 위험한 이유

"보안 위험"이 아니라 구체적으로:

- 다른 사용자가 파일 내용을 바꿀 수 있다. 실행되는 스크립트라면 임의 코드가
  그 스크립트를 실행하는 계정 권한으로 돌아간다.
- root가 cron으로 돌리는 스크립트라면 권한 상승(privilege escalation) 경로.

실무에서 `777`이 나오는 경위는 대개 이렇다:
컨테이너 볼륨 쓰기 실패 → 원인 파악 귀찮음 → `chmod 777` → 됨 → 배포.

> `777`은 해결이 아니라 진단 포기의 흔적이다.

## 실습에서 한 것

- `chmod` 실습: `644`/`711`/`311`/`000`/`755` 디렉토리 권한 조합 비교
- 변수 하나만 바꾸는 통제 실험으로 "디렉토리 `x` ≠ 파일 내용 읽기 권한" 증명
- `chmod +x`와 `chmod u+x`의 차이 확인 (`+x`는 소유자/그룹/기타 셋 다 켬)
- Module 001 `Lesson01.py`에 `PermissionError`가 실제로 발생하는 상황을 재현

### 재현 방법

```bash
mkdir -p ~/blocked/inner
chmod 000 ~/blocked          # 통과 권한 제거 → inner에 도달 불가
python3 Lesson01.py ~/blocked/inner
```

`shutil.disk_usage()`는 **그 경로가 속한 파일시스템 전체의 통계**를 반환하므로
디렉토리 안을 들여다보지 않는다. 그래서 읽기 권한이 없는 디렉토리를 넘겨도
`PermissionError`가 나지 않는다. 경로를 **따라가는 것 자체**가 막혀야 발생한다.

### 발견한 버그와 수정

예외를 `except OSError` 하나로 묶고 메시지는 `FileNotFoundError` 기준으로만
썼더니, 권한 문제가 `"Path not found"`로 잘못 보고됐다.

```python
except PermissionError as e:
    raise DiskCheckError(f"Permission denied for path : '{path}'") from e
except FileNotFoundError as e:
    raise DiskCheckError(f"Path not found : '{path}'") from e
except OSError as e:
    raise DiskCheckError(f"OS error checking path '{path}': {e}") from e
```

좁은 예외를 위에, 넓은 예외를 아래에. 순서를 바꾸면 아래쪽이 dead code가 된다.

> 잘못된 에러 메시지는 없는 것보다 나쁘다. 없으면 처음부터 조사하지만,
> 틀린 메시지는 잘못된 방향으로 시간을 태운다.

### 미실행 에러 경로

`except OSError` 블록은 이론상 `PermissionError`를 잡지만, 그 코드는 그때까지
**한 번도 실행된 적이 없었다.** 테스트도 `FileNotFoundError` 케이스만 있었다.

> 실행된 적 없는 에러 처리 코드는 동작한다는 보장이 없다.

정상 경로는 매일 수천 번 돌아 버그가 즉시 드러나지만, 에러 처리 경로는 몇 달에
한 번 실행되고 그때 처음 버그가 드러난다 — 이미 뭔가 잘못된 상황에서.
그래서 에러 경로를 일부러 발생시켜 테스트한다. (Chaos Engineering의 가장 작은 버전)

## Infrastructure 연결

### 컨테이너 권한 문제의 본질은 UID 불일치

리눅스는 사용자를 이름이 아니라 **UID(숫자)**로 식별한다. 컨테이너와 호스트는
UID 네임스페이스를 공유한다.

```
호스트:      /data 소유자 = eunho (UID 1000), 권한 755
컨테이너 안: 프로세스 실행자 = appuser (UID 1001)
→ 커널 입장에서 UID 1001은 "기타(other)" → r-x → 쓰기 실패
```

컨테이너 안에 그 이름이 있든 없든 상관없다. 이름은 `/etc/passwd`가 숫자에 붙인
라벨일 뿐이고 커널은 숫자만 본다. (컨테이너 안 `ls -l`에서 소유자가 숫자로 뜨는
경우가 그래서 생긴다)

해결 방향 세 가지:
- `docker run --user 1000:1000` — 호스트와 같은 UID로 실행
- 호스트 디렉토리 소유자를 컨테이너 UID에 맞춤
- 공유 그룹 + `g+w` + setgid

### 최소 권한 원칙

systemd 유닛에 `User=`를 지정하지 않으면 root로 돈다. 디스크 조회만 하는
스크립트에 root가 필요 없다. 필요 이상의 권한으로 프로세스를 돌리는 것은
그 자체로 보안 부채다.

### 그룹이 필요한 이유

소유자(한 명)와 기타(전부) 두 단계로는 "5명 중 특정 2명"을 표현할 수 없다.
그래서 그룹이 존재한다.

```
ml-team    → 팀 전원
data-eng   → 데이터 담당자
deployers  → 배포 담당자

/data/raw   소유자:data-eng, 그룹:ml-team, 750
/models     소유자:배포담당, 그룹:ml-team, 750
```

실제 사례: `journalctl`로 다른 사용자/시스템 메시지를 보려면 `adm` 또는
`systemd-journal` 그룹에 속해야 한다. root만도, 전체 공개도 아닌 중간 단계.

## 면접 포인트

- 파일 권한이 `644`로 정상인데 `Permission denied`가 나는 이유 →
  경로상 상위 디렉토리 중 하나에 `x`가 없음.
- 호스트에서 `755`로 만든 디렉토리를 컨테이너에 마운트했는데 쓰기 실패 →
  UID 불일치. 컨테이너 프로세스가 "기타"로 분류됨.
- `exit code 126` = 실행 권한 거부 (x 비트 또는 상위 디렉토리 x 확인)

## 내 말로 3줄 요약

1. 권한 체계의 핵심은 '누구인가'와 '첫 매칭'이다: 접근 주체가 소유자/그룹/기타 중
   어디인지 먼저 확인하며, 커널은 가장 먼저 일치하는 권한 규칙 하나만 적용한다.
2. 디렉토리 권한의 `x`는 통과(진입) 권한이다: 디렉토리에 `x`가 없으면 내부 파일
   접근·읽기가 모두 불가능하며, 파일 에러 처리 시 상위 디렉토리 권한을 함께 체크해야 한다.
3. 컨테이너 권한 문제는 UID 불일치에서 온다: 호스트와 컨테이너는 계정 이름이 아닌
   '숫자 ID(UID)'를 기준으로 검사하므로 불일치 시 `Permission denied`가 발생한다.
